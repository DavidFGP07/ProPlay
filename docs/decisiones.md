# Registro de decisiones técnicas

Una línea de justificación por decisión. Las que venían dadas por el documento
del proyecto se anotan igual, para que el registro esté completo.

## Estructura y herramientas

| Decisión | Justificación |
| --- | --- |
| Monorepo con **npm workspaces**, sin Nx ni Turborepo | Tres paquetes y un solo equipo: el orquestador extra añade configuración sin resolver nada todavía. |
| Monolito modular en lugar de microservicios | El acoplamiento entre módulos (matching necesita perfiles, estadísticas y ofertas) es alto y el tráfico esperado bajo. |
| Nombres de workspace `api`, `web` y `@proplay/shared` | `npm run build -w web` es el comando que pide Vercel; el paquete compartido va con ámbito para que se distinga de una dependencia externa. |
| `concurrently` para el `dev` de la raíz | Es la forma más simple de tener los dos procesos con prefijos de color en una sola terminal. |
| ESLint 9 con *flat config*: una base en la raíz que cada workspace extiende | Una sola lista de reglas, pero cada workspace mantiene su `eslint .` independiente. |
| Prettier no se añade | ESLint más `.editorconfig` cubren lo necesario; un formateador más significa otra configuración que mantener sincronizada. |

## Paquete compartido

| Decisión | Justificación |
| --- | --- |
| Los enums del dominio se declaran como tuplas `as const` y de ahí se derivan el tipo, el objeto de valores y el esquema Zod | Un solo sitio donde añadir un valor nuevo, sin listas paralelas que se desincronicen. |
| El frontend resuelve `@proplay/shared` con un **alias de Vite al TypeScript fuente** | Da recarga en caliente al cambiar el contrato y permite que `npm run build -w web` funcione sin compilar antes otro workspace, que es justo lo que rompe los despliegues en Vercel. |
| La API resuelve `@proplay/shared` con `paths` de TypeScript hacia el fuente en desarrollo y hacia `dist/*.d.ts` en `tsconfig.build.json` | `tsx` recarga en caliente sobre el fuente, y en la compilación `tsc` usa las declaraciones para no intentar emitir archivos de otro paquete. |
| `packages/shared` se compila a CommonJS | La API compila a CommonJS; un paquete ESM obligaría a migrar todo el backend a ESM sin ganancia. |
| Los tipos se re-exportan desde `types/` además de inferirse en `schemas/` | Cumple la estructura pedida y da un punto único de importación de tipos, sin duplicar declaraciones (son los mismos símbolos). |

## Backend

| Decisión | Justificación |
| --- | --- |
| Prisma como ORM | El `schema.prisma` sirve a la vez de documentación del modelo, que es un requisito del proyecto. |
| Validación con Zod en un middleware `validate(schema, fuente)` | Reutiliza los esquemas del contrato y deja los controladores sin código de validación. |
| El resultado validado de `query` se guarda en `req.validado.query` | En Express 5 `req.query` es de sólo lectura, así que no se puede sobrescribir con el valor coercido. |
| Access token de 15 minutos en memoria del cliente + refresh de 7 días en cookie `httpOnly` | Reduce la ventana de un token robado y evita guardar credenciales en `localStorage`. |
| El refresh token es **stateless** (JWT firmado, sin lista en Redis) | Suficiente para el alcance actual; cuando haga falta revocación inmediata se añade una lista de revocados en Redis. |
| La cookie de refresh se limita a la ruta `/api/v1/auth` | No viaja en las peticiones normales de la API, así que reduce su exposición. |
| `SameSite=None; Secure` sólo en producción, `Lax` en desarrollo | En producción la web y la API están en dominios distintos; en local ambos son `localhost` y `Lax` evita exigir HTTPS. |
| bcrypt con 12 rondas | Compromiso habitual entre coste de cómputo y resistencia a fuerza bruta. |
| El hash de contraseñas usa `bcryptjs` (JavaScript puro) en lugar de `bcrypt` (nativo) | Sin dependencia nativa, la imagen no necesita binarios precompilados ni toolchain y se construye de forma reproducible manteniendo `npm ci --ignore-scripts`; con `bcrypt`, ese flag omitía la descarga del binario y el contenedor no arrancaba. Mismo algoritmo y formato (`$2b$`): los hashes existentes siguen siendo válidos. A la escala del piloto, la diferencia de rendimiento es irrelevante. |
| El registro crea también el perfil (`PerfilJugador` o `PerfilEquipo`) en la misma transacción | Evita usuarios sin perfil, un estado que ningún módulo posterior sabría manejar. |
| Las variables de entorno se cargan con `process.loadEnvFile` de Node en lugar de `dotenv` | Node 20 ya lo trae; una dependencia menos para exactamente el mismo resultado. |
| `env.ts` valida con Zod y llama a `process.exit(1)` si algo falta | Fallar al arrancar es mucho más barato que fallar en la primera petición que use la variable. |
| El cliente de Redis usa `lazyConnect` | Las pruebas de integración pueden cargar la app sin Redis y el servidor conecta explícitamente al arrancar. |
| `GET /health` responde 200 si Postgres y Redis están arriba y 503 si alguno falla | Así lo puede usar directamente el health check de la plataforma de despliegue. |
| El rate limiting se desactiva con `NODE_ENV=test` | Las pruebas de autenticación hacen más de diez peticiones seguidas al mismo endpoint. |
| Los errores de dominio son clases en `utils/errors.ts` y un único `errorHandler` los traduce | Garantiza la misma forma de respuesta en toda la API y que el stack no salga nunca en producción. |
| El módulo `perfiles` queda como andamiaje | La lista de criterios de aceptación no incluye ninguno de sus endpoints; implementarlo sería añadir funcionalidad no pedida. |
| Los stubs del andamiaje lanzan `NotImplementedError` desde el *repository*, no desde el controlador | Deja el camino controller → service → repository ya recorrido, que es la estructura que hay que respetar al implementar. |
| `prisma` está en `dependencies` y no en `devDependencies` | El `CMD` del contenedor ejecuta `prisma migrate deploy`, así que el CLI tiene que existir en la imagen de producción. |

## Datos

| Decisión | Justificación |
| --- | --- |
| Entidades y campos del modelo en español | Están así en el documento del proyecto y el esquema hace de documentación. |
| `PerfilVector` guarda el vector dos veces: `dimensiones Float[]` y `embedding vector(64)` | Prisma sabe leer y escribir el array; la columna nativa de pgvector es la que permite búsquedas de similitud. |
| La columna `vector(64)` se declara como `Unsupported("vector(64)")` en el schema y se crea en una migración escrita a mano | Prisma no modela el tipo, pero declararlo evita que lo considere deriva del esquema en la siguiente migración. |
| El índice ANN (`ivfflat`) queda como TODO en la migración | Un índice aproximado sobre una tabla vacía no aporta nada y sus parámetros dependen del volumen real. |
| El seed es idempotente (`upsert`) e incluye además un ADMIN y un SCOUT | Se puede ejecutar varias veces sin ensuciar la base, y hacen falta cuentas de esos roles para probar `rbac`. |
| Los datos sintéticos salen de un generador pseudoaleatorio con semilla fija | El seed produce siempre los mismos números, así las pruebas manuales son comparables entre máquinas. |
| Las pruebas de integración corren contra una base real, no contra mocks | Lo que se quiere verificar es justo la integración: Zod, Prisma, middlewares y Express juntos. |
| Las pruebas crean usuarios con correo aleatorio prefijado y los borran al terminar | Permite ejecutarlas contra la base de desarrollo sin arrastrar basura ni chocar entre ejecuciones. |

## Frontend

| Decisión | Justificación |
| --- | --- |
| El access token vive en un módulo en memoria, no en `localStorage` | Un token en `localStorage` es accesible desde cualquier script de la página. |
| Un solo interceptor de axios refresca la sesión y reintenta la petición una vez | Concentra el manejo del 401 en un sitio y evita bucles de refresco. |
| El estado de servidor lo lleva TanStack Query; la sesión, un contexto de React | Query no está pensado para el ciclo de vida de la autenticación, y el contexto es lo bastante simple. |
| La paleta de marca se define con `@theme` en `src/index.css` (Tailwind 4) como `brand`, `accent` y `surface` | Viene del prototipo de `Fronted`; los nombres semánticos sobreviven a un cambio de color, los hexadecimales sueltos no. |
| El tema es oscuro fijo | Es la convención del sector; el fondo es el token `surface-900` del prototipo. |

## Infraestructura y despliegue

| Decisión | Justificación |
| --- | --- |
| Postgres y Redis en Docker Compose, pero api y web fuera de Docker | La recarga en caliente y los tiempos de arranque son mucho mejores en local. |
| Imagen de la API multi-stage sobre `node:22-alpine` con usuario no root | Menos superficie y menos privilegios en la imagen final. |
| El contexto de build del Dockerfile es la raíz del monorepo | La imagen necesita `packages/shared`; construir desde `apps/api` no lo alcanzaría. |
| La imagen de producción instala dependencias con `npm ci --omit=dev` de todos los workspaces | `npm ci` exige el árbol completo de workspaces del lockfile; filtrar por workspace daría un lockfile incoherente por unos pocos megas de diferencia. |
| El `CMD` ejecuta `prisma migrate deploy` antes de arrancar | El despliegue queda en un paso y la base nunca se queda atrás del código. |
| `trust proxy` sale de `TRUST_PROXY`, desactivado si no se fija y obligatorio en producción | Con un valor fijo y sin proxy delante, Express tomaría la IP de `X-Forwarded-For`, que el cliente puede escribir: bastaría cambiarla en cada petición para saltarse cualquier límite por IP. Sólo el despliegue sabe cuántos proxies hay; `true` se rechaza porque confía en cualquiera. |
| `vercel.json` reescribe todas las rutas a `index.html` | Sin eso, recargar una URL profunda de React Router devuelve 404. |
| El CI usa `prisma migrate deploy` sobre una base `proplay_test` | `migrate dev` es interactivo y pensado para desarrollo. |
| Verificación local con Postgres 17 de Homebrew en lugar de Docker | En la máquina donde se construyó el esqueleto no había Docker; Homebrew compila pgvector contra 17, y `docker-compose.yml` sigue fijando 16 como dice la especificación. |

| Cambiar la contraseña revoca las demás sesiones mediante `Usuario.credencialesCambiadasEn` | Los refresh tokens son JWT sin estado y no se guardan, así que no hay lista que revocar. `/auth/refresh` rechaza los emitidos antes del último cambio de credenciales, comparando en segundos (`iat < floor(credencialesCambiadasEn / 1000)`) para que el token de la propia respuesta siga valiendo; esa respuesta trae una sesión nueva y quien cambia la contraseña sigue dentro. Los access tokens ya emitidos valen hasta caducar (15 minutos como máximo). |
| Una contraseña actual incorrecta responde `400 CONTRASENA_ACTUAL_INVALIDA`, no `401` | El interceptor del cliente trata cualquier `401` como sesión caducada: refresca, reintenta y cierra la sesión. Con un `401`, equivocarse de contraseña al cambiarla expulsaría al usuario. |
| `PATCH /usuarios/me` deja de aceptar `activo` | Suspender o reactivar una cuenta no es una edición propia: cualquier usuario podía suspenderse y uno suspendido con un access token vigente podía reactivarse. Queda para el módulo `admin`; si llega, el campo se descarta. |
| Lista de rutas sin datos de demostración (`RUTAS_SIN_DATOS_DEMO` en `router/areas.ts`) | El aviso «Datos de demostración» lo pinta el `Layout` para todas las vistas; las que sólo consumen endpoints reales, como `/cuenta`, se declaran ahí y no lo muestran. Al conectar cada vista de verdad, se añade su ruta. |
| El primer administrador se da de alta con un script, `npm run admin:promover -w api -- <correo>` (en producción, `node apps/api/dist/cli/promoverAdministrador.js`), que promueve a `ADMIN` una cuenta **ya registrada como scout** | La contraseña la define la persona al registrarse y nunca pasa por argumentos ni por el historial de la terminal. Un script es explícito y deja traza; una variable `ADMIN_EMAIL` aplicada al arrancar se reaplicaría en cada despliegue y el seed crea cuentas con la contraseña de demostración. Se niega con cuentas de jugador o de equipo (su perfil público quedaría huérfano), desactivadas o inexistentes; si ya es administrador no hace nada. El rol y la traza `ROL_CAMBIADO` (`metadata: { rolAnterior, rolNuevo, origen: "cli" }`) van en la misma transacción. No revoca sesiones: el refresco lee el rol de la base, así que el nuevo llega en el siguiente refresco (15 minutos como máximo). La lógica vive en `usuarios.service` y el script en `src/cli/` para que se compile en la imagen, que no trae `tsx`. |

## Ubicación del jugador

| Decisión | Justificación |
| --- | --- |
| La ubicación geográfica del jugador es **país + departamento**: `PerfilJugador.pais` (`CHAR(2)`, ISO 3166-1 alfa-2) y `PerfilJugador.departamento` (enum `Departamento`), éste sólo cuando el país es Colombia. Sustituye a `PerfilJugador.region` | La fórmula de la dimensión geográfica (prototipo y `docs/arquitectura.md`) tiene tres niveles: misma ubicación, misma macrorregión y otra, más la disposición a relocalizarse. El departamento basta para los tres; la ciudad sería un dato personal más sin mejorar el cálculo (Ley 1581), y la zona horaria se deduce del país. `region` mezclaba conceptos: el seed guardaba regiones de servidor (LAN, LAS…) y el prototipo, ciudades. La región de servidor sale de la cuenta vinculada (S2). |
| Catálogo: `DEPARTAMENTOS` es enum en `shared` y en Prisma (33 valores); `PAISES` es una constante de `shared` validada con Zod, no enum de Prisma; `MACROREGION_POR_DEPARTAMENTO` deriva la macrorregión y no se guarda | Los departamentos son un conjunto cerrado y estable: que la base lo garantice compensa. La lista ISO es larga y la mantiene un tercero. La macrorregión es función del departamento: guardarla permitiría incoherencias. Nada de texto libre; las etiquetas visibles van al i18n del cliente. |
| Un departamento que abarca varias regiones naturales cuenta en una sola, como en las regiones administrativas de planificación (Cauca, Chocó, Nariño y Valle del Cauca, Pacífica; Antioquia, Andina). San Andrés cuenta como Caribe y no hay macrorregión Insular | Para el piloto, centrado en el Caribe colombiano, el archipiélago es parte del segmento Caribe. Con San Andrés en Caribe, ningún departamento quedaba Insular. |
| Regla de ubicación en el contrato (`ubicacionJugadorSchema`, incluido en `perfilJugadorSchema`): con `CO` el departamento es obligatorio y con otro país no se admite. `null` borra la ubicación | Un departamento sin país no se puede comprobar en el esquema; el servidor lo valida contra el país guardado (ver la entrada del `PATCH /perfiles/jugador`). |
| La ubicación se captura en la edición del perfil (`PATCH /perfiles/jugador`), no en el registro ni en un onboarding | El registro dejó de pedirla porque es un dato del perfil, no de la cuenta; pedirla allí añade fricción al alta y no cubre a los jugadores ya registrados. El onboarding es una vista cuyo contenido principal es vincular la cuenta de Riot (S2). El endpoint es el primero del módulo `perfiles`, que la tarea siguiente completa. |
| El filtro de ubicación del buscador de talento (`busquedaJugadoresSchema`) pasa de `region` a `pais` + `departamento` | Filtraba una columna que deja de existir. El endpoint sigue en 501. |
| La migración `ubicacion_perfil_jugador` descarta los valores de `pais` (`USING NULL`) en vez de convertirlos | Eran texto libre del seed («Colombia»); truncarlos a dos caracteres daría códigos falsos. Cada base local debe ejecutar `npm run db:deploy` y `npm run db:seed`, que repone la ubicación de los 15 jugadores. |
| `GET /perfiles/me` responde `{ tipo, perfil }` según el rol; al scout y al administrador, que no tienen perfil, `200 { tipo: null, perfil: null }`. `PATCH /perfiles/jugador` es una actualización parcial y responde con la misma forma | El cliente puede reutilizar la respuesta del `PATCH` como la de `GET /me` en la caché de TanStack Query. Con un `404`, TanStack Query reintentaría y cualquier vista común que pida el perfil mostraría un error para dos roles válidos. El `404` queda para la inconsistencia de un jugador o equipo sin perfil. |
| Cuando el `PATCH` trae el país, el servidor guarda el departamento con él (nulo si no llega). Si trae sólo el departamento, lo valida contra el país guardado con la misma regla de `ubicacionJugadorSchema` (`422` si no casa) | Así cambiar de Colombia a otro país no deja el departamento anterior guardado, y un jugador de Colombia puede cambiar de departamento sin reenviar el país. La regla vive una sola vez en `shared`: el esquema comprueba la pareja cuando llega completa y el servicio la reaplica sobre el país guardado. Sustituye a la regla anterior, que rechazaba cualquier departamento sin país. |
| Actualizaciones parciales con `PATCH` en toda la API. `PUT /perfiles/jugador` pasa a `PATCH`, y `PUT /perfiles/equipo` también, aunque sigue en 501 | Ni el documento ni `docs/arquitectura.md` fijaban el verbo: el `PUT` venía del andamiaje. `PUT` reemplaza el recurso entero y estas rutas sólo cambian los campos enviados, como `PATCH /usuarios/me` y `PATCH /ofertas/:id`. Un `PUT` futuro sólo tiene sentido si reemplaza el recurso completo. |
| La tarjeta «Ubicación» de `/mi-perfil` habla con la API real (`GET /perfiles/me`, `PATCH /perfiles/jugador`) mientras el resto de la vista sigue con datos de demostración. Es **temporal**: la tarea siguiente conecta la vista entera | La dimensión geográfica necesita la ubicación antes del S3 y la vista completa depende del resto del módulo `perfiles`. Para no confundir el dato real con los de la persona de ejemplo, la tarjeta lleva borde verde, la insignia «Dato real de tu cuenta» y, con el puente activo, una línea que lo explica. Se monta fuera de la rama que depende del puente, así que también aparece con `VITE_DEMO_DATA` apagado. La región y la disposición a relocalizarse salen del panel simulado de «Datos profesionales» para que no haya dos formularios del mismo dato. `/mi-perfil` no entra en `RUTAS_SIN_DATOS_DEMO` hasta que la vista entera sea real. |
| La tarjeta avisa «Completa tu ubicación» cuando el jugador no tiene país guardado; no hay bloqueo ni ventana emergente | Es la forma con menos fricción de recuperar a los jugadores registrados antes de la tarea 1.5. El S3 decide qué puntúa la dimensión geográfica mientras falte (ver «Pendientes»). |
| Los países se muestran con `Intl.DisplayNames` en español a partir del código ISO; los departamentos y macrorregiones, con etiquetas de `i18n/es.ts` | 249 nombres de país mantenidos a mano serían deuda sin valor: el navegador ya los trae localizados. Colombia va primero en la lista por el piloto. |
| El traductor de errores de la API a formularios (`api/errores.ts`) y el aviso de resultado con reintento (`EstadoEnvio` en `components/ui.tsx`) salen de `CuentaPage` a piezas compartidas | La tarjeta de ubicación los necesitaba igual; CLAUDE.md §5 pide que los estados transversales no se reescriban por vista. Los textos comunes pasan a `es.comun`. |
| El aviso de privacidad precisa «ubicación (país y, en Colombia, departamento)» en lugar de «región» **sin subir `VERSION_AVISO_PRIVACIDAD`**, que sigue en 1.0 | El aviso aún no se ha publicado: el versionado cuenta desde la primera publicación. A partir de ella, cualquier cambio del texto sube la versión. |

## Perfil público y módulo `perfiles`

| Decisión | Justificación |
| --- | --- |

Salen de la vista el `@handle`, los roles preferidos, los años de experiencia, los equipos anteriores y el anillo de verificación de la cabecera: no tienen modelo detrás (ver «Pendientes»). |

Con `VITE_DEMO_DATA` apagado esas secciones no se montan y la vista queda con la cabecera y los datos profesionales. Se retiran a medida que se conecten sus módulos (S2: cuentas y estadísticas; tarea 2.2: habilidades). |
| El servidor recorta la presentación y guarda una en blanco como `null` | `perfilJugadorSchema` no admite `null` en `bio` y el formulario envía el texto vacío para borrarla; sin normalizar, el perfil público mostraría un párrafo vacío en lugar de su estado «todavía no ha escrito su presentación». |

Los mensajes propios de un esquema («Selecciona el departamento») tienen prioridad y no pasan por el mapa. Las reglas siguen saliendo del contrato: el mapa sólo cambia el texto. |

La presentación y la disponibilidad del jugador no cambian en este PR: la disponibilidad sigue como límite conocido (entrada anterior). |

| La oferta pasa por `BORRADOR → ABIERTA → CUBIERTA` o `→ CERRADA` (también `BORRADOR → CERRADA`). `CUBIERTA` es un estado nuevo y exige al menos una postulación `ACEPTADA`. Los estados finales no se reabren: para volver a buscar, se publica otra oferta. Las transiciones están en `TRANSICIONES_OFERTA` (`shared`) | El tiempo hasta cubrir la vacante mide H1, y sólo se calcula si se distingue una vacante cubierta de una cerrada sin contratar. Reabrir haría que una misma oferta tuviera varios tiempos hasta cubrirla. |
| `Oferta.publicadaEn` (paso a `ABIERTA`) y `Oferta.cerradaEn` (paso a `CUBIERTA` o `CERRADA`) | Son el inicio y el final del tiempo hasta cubrirla. `creadoEn` no sirve: un borrador puede esperar días antes de publicarse. |
| La postulación pasa por `ENVIADA → EN_REVISION → ENTREVISTA → ACEPTADA`, sin saltos, y se puede rechazar desde cualquier estado no final. `ENTREVISTA` es el tryout del documento («invitar a un tryout») y la interfaz lo muestra como «Tryout / entrevista». Transiciones en `TRANSICIONES_POSTULACION` | Es un paso real del embudo. Que no haya saltos asegura que cada etapa alcanzada tenga su fecha. |
| La fecha de cada cambio de estado se guarda en **columnas de `Postulacion`** (`revisadaEn`, `entrevistaEn`, `aceptadaEn`, `rechazadaEn`; el envío es `creadoEn`), no en una tabla de historial. La correspondencia está en `FECHA_POR_ESTADO_POSTULACION` | Como la máquina de estados no tiene vueltas atrás, cada columna se escribe una sola vez y el embudo sale de una consulta sin agregaciones. Una tabla de historial sería la entidad 16 y apartaría el modelo del documento sin dar más información: el registro de quién hizo cada cambio y cuándo ya va a `AuditLog`, en la misma transacción (RNF-06). |
| Una transición no permitida responde **409** (`TRANSICION_NO_PERMITIDA`), no 422 | La petición es válida, pero no casa con el estado actual del recurso. En esta API el 422 ya significa error de validación del cuerpo (`ValidationError`). |
| Al pasar una oferta a `CUBIERTA` o `CERRADA`, las postulaciones que aún no estén en un estado final pasan a `RECHAZADA` en la misma transacción, con su `rechazadaEn` y su traza en `AuditLog` (`metadata.origen: "cierre_oferta"`) | Así el embudo no arrastra postulaciones abiertas en vacantes cerradas, y el jugador ve un estado final. El origen distingue este rechazo automático de una decisión del equipo sobre el candidato. |
| Los pesos de la oferta son **cinco columnas `Float`** (`pesoTecnica`… `pesoDisponibilidad`), sin valor por defecto en la base. El contrato los expone como el objeto `pesos`, con los nombres de `PESOS_MATCHING`. `pesosMatchingSchema` exige cada peso entre 0 y 1 y la suma igual a 1 (±`TOLERANCIA_SUMA_PESOS`); sin pesos, `crearOfertaSchema` aplica `PESOS_MATCHING` | Con columnas, el motor de matching los lee ya tipados y la analítica «qué dimensión decide» se hace en SQL plano. Sin `@default` en Prisma, los valores por defecto viven sólo en `shared`: en la propuesta se planteaba un `@default` con una prueba que lo comparara con `PESOS_MATCHING`, pero al vaciar la tabla en la migración (entrada siguiente) ya no hace falta rellenar filas existentes. Un peso 0 se admite: anula una dimensión que al equipo no le importa. |
| La migración `ofertas_estados_pesos_ubicacion` borra las ofertas existentes (`DELETE FROM "Oferta"`) antes de cambiar el modelo | Sólo podían venir del seed, porque crear ofertas respondía 501, y no caben en el modelo nuevo: `rol` tenía roles de otros juegos y faltan modalidad y pesos. Borrarlas es más honesto que inventar valores. El borrado arrastra sus postulaciones y matchings, también del seed. Cada base local debe ejecutar `npm run db:deploy` y `npm run db:seed`. |
| La ubicación de la oferta es **`modalidad`** (`PRESENCIAL`, `HIBRIDA`, `REMOTA`) **+ `pais` + `departamento`**, con el catálogo del jugador. `REMOTA` es la oferta «sin restricción» y no lleva ubicación; `PRESENCIAL` e `HIBRIDA` exigen país y, en Colombia, departamento (`ubicacionOfertaSchema`). Sustituye a `Oferta.region` | La dimensión geográfica compara la ubicación del jugador con la de la oferta, y `docs/arquitectura.md` la define también por la «participación en línea». `region` guardaba regiones de servidor. La regla país-departamento se escribe una sola vez (`validarPaisDepartamento`, en `schemas/common.ts`) y la usan jugador, equipo y oferta. |
| La sede del equipo pasa de `PerfilEquipo.region` a `pais` + `departamento`, opcionales y con la misma regla que el jugador. `PATCH /perfiles/equipo` la edita (si llega sólo el departamento, se valida contra el país guardado) y `GET /perfiles/me` la devuelve | Sustituye a la entrada «`region` sale de `perfilEquipoSchema`… hasta que exista el catálogo de ubicación del S3» de «Perfil público y módulo `perfiles`»: el catálogo ya existe. La interfaz la edita en el PR de las vistas del equipo. |
| `rol` de la oferta es el enum **`PosicionLol`** (`TOP`, `JUNGLA`, `MID`, `ADC`, `SOPORTE`) y `juego` lo fija el servidor con `JUEGO_PILOTO`; el cliente ya no lo envía. Las 5 ofertas del seed pasan a League of Legends | El piloto es sólo de League of Legends. Con texto libre, el filtro por rol y la dimensión técnica comparaban cadenas sin catálogo. Las cinco posiciones corresponden a `teamPosition` de la API de partidas de Riot. `rangoMinimo` sigue como texto hasta que exista el catálogo de rangos (ver «Divergencias», `rango`). |
| `experienciaMinAnios` sale del contrato y de `Oferta` | El documento define la experiencia como trayectoria (equipos, torneos, logros), no como años, y el modelo de trayectoria sigue pendiente (ver «Pendientes»). Lo que la oferta deba exigir lo decidirá ese modelo. `OfertaParaMatching` lo usa todavía: lo ajusta quien implemente el motor. |
| Permisos: un equipo sólo gestiona sus propias ofertas y una ajena responde **403**; un `BORRADOR` ajeno responde **404**. El jugador no puede postularse dos veces (409) ni a una oferta que no esté `ABIERTA` (409). El scout y el administrador sólo leen | Las ofertas publicadas las ve cualquier usuario con sesión, así que ocultar que existen no protege nada, y el 403 es más fácil de depurar. Un borrador sí es privado. |
| El scout ve las postulaciones de cualquier oferta publicada, no sólo las de una organización | El modelo no relaciona al scout con ningún equipo. Para el piloto se acepta, pero el aviso de privacidad lo dice expresamente: el párrafo «Quién ve tus datos» decía «las postulaciones que reciben», que no cubría a un scout que no recibe ninguna. El texto nuevo enumera los datos de la postulación que se ven y aclara que la ven todos los scouts registrados. `VERSION_AVISO_PRIVACIDAD` sigue en 1.0 porque el aviso no se ha publicado. Del jugador, la postulación recibida sólo expone campos de su perfil público; el correo no sale (el sustituto de la mensajería, tarea 3.18, va aparte). |
| `GET /ofertas` lista sólo ofertas `ABIERTA`, paginadas (`paginacionQuerySchema`) y de la más reciente a la más antigua (`publicadaEn`), con filtros de rol, departamento y modalidad. Las del propio equipo, en cualquier estado, van por `GET /ofertas/me`; las postulaciones del jugador, por `GET /ofertas/postulaciones/me` | El orden por compatibilidad llega con el motor de matching. Separar «mis ofertas» evita una respuesta que cambie de forma según el rol. |
| No se publican eventos de los cambios de estado | No existe ningún mecanismo de eventos en la API y las notificaciones pasaron a fase 2. Se crea cuando llegue ese módulo. |
| Los cambios de estado de ofertas y postulaciones se escriben con una actualización condicionada al estado leído (`updateMany … where: { id, estado }`): si otra petición lo cambió antes, responden 409 `TRANSICION_NO_PERMITIDA` | Sin bloqueos ni transacciones serializables: dos cambios simultáneos sobre la misma postulación no pueden saltarse la máquina de estados ni sobrescribir una fecha ya guardada. |
| Otros 409 del módulo: `OFERTA_FINALIZADA` (editar una oferta cubierta o cerrada), `OFERTA_SIN_ACEPTADA` (cubrir sin ninguna postulación aceptada), `OFERTA_NO_ABIERTA` (postularse a una oferta que no está abierta o cambiar el estado de una postulación de una oferta que ya no lo está) y `POSTULACION_DUPLICADA` | Todos son conflictos con el estado del recurso, no errores del cuerpo. Un código propio por caso deja que el cliente muestre el mensaje adecuado sin interpretar el texto. Al cerrar la oferta sus postulaciones quedan resueltas, así que no se pueden seguir moviendo. |
| Editar la modalidad o la ubicación de una oferta aplica la misma lógica que la ubicación del jugador: si llega el país, el departamento va con él (nulo si no se envía); si llega sólo el departamento, se combina con el país guardado; pasar a `REMOTA` borra la ubicación. El resultado se valida entero con `ubicacionOfertaSchema` (422 si no casa) | El cuerpo de un `PATCH` es parcial y el esquema no ve lo guardado; validar la combinación evita una oferta presencial sin ubicación o una remota con departamento. |
| Las escrituras de ofertas y postulaciones son sólo del rol `EQUIPO`: se quita `ADMIN` de los `rbac` del andamiaje. `GET /ofertas/:id/postulaciones` admite `EQUIPO` (sólo de sus ofertas), `SCOUT` y `ADMIN` | El administrador no tiene perfil de equipo ni panel (decisión 0.10): sus operaciones van por scripts. Leer sí le sirve para soporte. |
| `GET /ofertas/:id/postulaciones` y `GET /ofertas/postulaciones/me` no se paginan | Son las postulaciones de una oferta o de un jugador: decenas como mucho en el piloto. Si crecen, se paginan con `paginacionQuerySchema` como el listado de ofertas. |
| Explorar oportunidades (`/vacantes`), el detalle de la oferta (`/vacantes/:id`) y la pestaña «Postulaciones» de Mi perfil hablan con la API real, sin puente de demostración; `/vacantes` y `/vacantes/:id` entran en `RUTAS_SIN_DATOS_DEMO` | Son las vistas del jugador del recorte (decisión 0.10). Los hooks reales (`useOfertas`, `useOferta`, `useMisPostulaciones`, `usePostular`) leen las respuestas con los esquemas de `shared`, que convierten las fechas. Los del lado del equipo (`useVacantes`, `usePostulaciones`, `useCrearOferta`…) siguen simulados hasta el PR de las vistas del equipo, porque `/panel-equipo` todavía los usa. |
| El detalle de la oferta **pierde el ranking simulado**: los pesos ajustables, el ranking de candidatos, su desglose, la explicación en lenguaje natural y la traza. Muestra los pesos **reales** que eligió el equipo, en sólo lectura, y una nota de cómo se calculará la compatibilidad | La simulación calcula el ranking con ids del prototipo y con una oferta real devolvería una lista vacía. Mezclarlo con datos reales contradiría la verificabilidad. El ranking con su desglose es la vista del núcleo que construye la tarea siguiente sobre el motor real. El código del prototipo sigue en el historial de git y en `lib/matching.ts`. Resuelve también el riesgo para demostraciones de los enlaces del ranking a perfiles simulados. |
| El listado de ofertas no muestra puntaje ni el bloque «Cómo se construye el ranking» | Sin motor de matching no hay puntaje que mostrar. El orden es por fecha de publicación y el subtítulo lo dice. |
| Las ofertas se filtran por posición, departamento y modalidad con selects, y se pagina con «Anterior» / «Siguiente» (`Paginacion`, en `components/ui.tsx`). Cambiar un filtro vuelve a la primera página y la página anterior se mantiene en pantalla mientras llega la siguiente (`keepPreviousData`) | Son los filtros del contrato (`listarOfertasQuerySchema`). La búsqueda por texto del prototipo no tiene endpoint y no se mantiene. |
| `?pestana=postulaciones` abre esa pestaña de Mi perfil; el detalle de la oferta enlaza ahí tras postularse | Mis postulaciones no tiene vista propia (decisión 0.10). Un parámetro de la URL deja enlazarla sin crear otra ruta. La pestaña es real y se muestra también con el puente apagado. |
| El `Modal` compartido se pinta con un portal en `document.body` | `.card` usa `backdrop-filter`, que convierte el `position: fixed` del diálogo en relativo a la tarjeta y lo recortaba cuando el modal se abría desde dentro de una. Lo destapó el botón «Postularme» de la cabecera del detalle. |
| Crear y editar oferta es una vista propia del área del equipo: `/panel-equipo/ofertas/nueva` y `/panel-equipo/ofertas/:id/editar`, en un área nueva del enrutador, `gestionOfertas` (sólo `EQUIPO`), declarada en `router/areas.ts` como las demás. Sustituye al modal «Publicar vacante» del panel | Es una vista del núcleo (el inventario de CLAUDE.md §5 no le daba ruta) y el formulario con cinco deslizadores no cabe bien en un modal a 375 px. El scout ve lo mismo que el equipo salvo crear y editar ofertas, así que el área lo excluye en lugar de que la vista lo compruebe. La edición reutiliza el formulario; una oferta ajena, cubierta o cerrada muestra el estado «sin permiso». |
| Los deslizadores de pesos siempre suman 100 %: mover uno reparte el resto entre los demás en proporción a sus pesos. El estado guarda porcentajes **con decimales** y sólo se redondea, por el método del resto mayor, al mostrarlos y al enviarlos (`lib/pesos.ts`) | Con el estado en enteros, mover un deslizador paso a paso con el teclado arrastraba el error de redondeo siempre hacia la misma dimensión: de 35 a 40 en la técnica, la experiencia bajaba de 20 a 15 en vez de a 18. Lo destapó la verificación en el navegador; la prueba «mover paso a paso conserva la proporción» lo fija. Son `input type="range"` con etiqueta y `aria-valuetext`, así que funcionan con teclado y lector de pantalla. |
| La gestión de la oferta vive en su detalle (`/vacantes/:id`) para el equipo dueño: editar, publicar, marcar como cubierta y cerrar, según `TRANSICIONES_OFERTA`. Cubrir y cerrar piden confirmación y avisan de cuántas postulaciones en proceso se rechazarán | El cierre rechaza las postulaciones pendientes (ver «Ofertas y postulaciones») y no tiene vuelta atrás. Mostrar el número evita cerrarlas sin querer. |
| Las postulaciones recibidas, dentro del detalle de la oferta, muestran sólo las transiciones permitidas desde su estado (`TRANSICIONES_POSTULACION`), cada botón con el nombre del jugador en su nombre accesible. El scout y el administrador las ven sin botones; un equipo ajeno no las ve | Es la vista de soporte acordada (sin vista propia, decisión 0.10). El enlace «Ver perfil» lleva al perfil público real del jugador (`/jugador/:id`). |
| El panel del equipo pierde las secciones simuladas «Mis vacantes» y «Procesos de selección», y gana «Tus ofertas» (`GET /ofertas/me`), real. Los indicadores y las recomendaciones del motor siguen simulados, con su marca, y son lo único que aún usa `useVacantes` y `usePostulaciones` del puente | La gestión de cada proceso ya está en el detalle de la oferta: repetirla en el panel con datos simulados confundiría. Los indicadores los sustituye la analítica (tarea 4.10) y las recomendaciones, el motor de matching. |
| La sede de la organización (país y departamento) se edita en «Datos de la organización», con la misma regla que la ubicación del jugador. Las opciones de país y departamento salen de `lib/ubicacion.ts` (`opcionesPais`, `OPCIONES_DEPARTAMENTO`), compartidas con el perfil del jugador y el formulario de oferta | Cierra el último hueco de la ubicación de la organización. Una sola lista ordenada, en lugar de tres copias. |
| En el formulario de oferta, la modalidad «Remota» sustituye los campos de país y departamento por una nota que explica que la oferta no lleva ubicación; fuera de Colombia, el departamento se desactiva con la pista «Sólo se pide en Colombia». Los campos desactivados de `components/ui.tsx` (`Input`, `Select`, `Textarea`) se ven apagados y con cursor de prohibido | Antes los campos desactivados se veían igual que los activos y parecía que no respondían al clic (lo reportó el usuario probando una oferta remota). El estilo vale para todos los formularios: el departamento del perfil del jugador y de la sede tenía el mismo problema. |

## Vinculación con Riot

| Decisión | Justificación |
| --- | --- |
| La propiedad de la cuenta de League of Legends se verifica con un **icono de invocador asignado**, no con el código de verificación de terceros ni con RSO. El jugador introduce su Riot ID (`nombre#etiqueta`) y su servidor; ProPlay resuelve la cuenta (account-v1 y summoner-v4) y le pide uno de los iconos básicos que tienen todas las cuentas, distinto del que lleva puesto; el jugador se lo pone en el cliente y pulsa «Verificar»; ProPlay compara `profileIconId` en summoner-v4 | El endpoint de código de verificación de terceros (`/lol/platform/v4/third-party-code/...`) **lo retiró Riot en 2022**: dejó de funcionar el 7 de marzo de 2022 y ya no figura en la API (fuentes abajo). RSO sólo se concede con clave de producción, y el piloto se construye con la de desarrollo. El icono funciona con ésta y el perfil se sigue construyendo con datos de la API oficial. Cambia la garantía: demuestra que el jugador controla la cuenta, no que conoce un secreto. Sustituye al «flujo OAuth» de la tarea 2.3 del plan. |
| **Superada por «Integración con Riot»** (el desafío caduca a los 15 minutos y los intentos los limita `limiteVinculacionRiot`, 10 cada 15 minutos por usuario). Condiciones del reto: icono distinto del actual, caducidad de unos 10 minutos, intentos limitados | Exigir un cambio hace despreciable que la cuenta de otro ya lleve por casualidad el icono pedido; la caducidad y el límite acotan los intentos de adivinarlo. |
| **Superada por «Integración con Riot»** (el desafío viaja como un JWT firmado y no se guarda nada entre los dos pasos). El reto pendiente vive en **Redis** con caducidad (puuid, servidor, Riot ID, icono pedido e icono inicial), y la fila de `CuentaGaming` sólo se crea al verificar | Una fila pendiente ocuparía el `puuid` en `@@unique([plataforma, externalId])`: bastaría con empezar la verificación de una cuenta ajena para bloquearla, y Prisma no modela índices únicos parciales. El reto no es secreto (el icono de una cuenta lo ve cualquiera), así que se guarda en claro. |
| **Superada por «Integración con Riot»** (el Riot ID se guarda en `handle` como `nombre#etiqueta` y `servidor` es texto validado con `SERVIDORES_LOL`, no enum de Prisma). `CuentaGaming`: `externalId` guarda el `puuid`; se añaden el Riot ID (nombre y etiqueta) y `servidor` (enum `ServidorLol`: LA1, LA2, NA1, BR1…, en `shared` y en Prisma en el mismo commit). `accessToken`, `refreshToken` y `expiraEn` se conservan sin uso | El índice único que ya existe impide vincular un `puuid` a dos usuarios. El servidor es la región de juego, distinta de la ubicación geográfica (ver «Ubicación del jugador»). Los campos de tokens son opcionales y ya están pensados cifrados: quitarlos para volver a añadirlos con RSO costaría dos migraciones. |
| **Superada por «Integración con Riot»** (sin `RIOT_API_KEY` la API arranca y sólo las rutas de Riot responden 503; sigue viajando sólo en la cabecera `X-Riot-Token`). `RIOT_API_KEY` es obligatoria fuera de `test`; viaja sólo en la cabecera `X-Riot-Token` (nunca en la URL), se oculta en los registros y no aparece en los errores | Es un secreto del servidor; en la URL acabaría en registros de proxies y en mensajes de error. |
| **Riesgo:** el `puuid` va cifrado por titular de la clave («unique per API Key holder»), así que los guardados con la clave de desarrollo podrían no valer con la de producción. **Mitigación:** guardar el Riot ID junto al `puuid` y, al cambiar de clave, volver a resolverlo con account-v1 | Sin el Riot ID, un cambio de clave dejaría huérfanas todas las cuentas vinculadas y obligaría a cada jugador a repetir la verificación. |
| **Trabajo futuro:** RSO (OAuth 2.0 de Riot) cuando haya clave de producción | Es el mecanismo que Riot recomienda para demostrar la propiedad; los campos de tokens ya están en el modelo. |

## Buscador de talento

Tarea 3.8 del plan: contrato y modelo, el endpoint `GET /scouting/jugadores` y
la vista `/explorar`.

| Decisión | Justificación |
| --- | --- |
| El rango es un **único enum ordenado, `RangoLol`** (31 valores, de `HIERRO_IV` a `RETADOR`), en `shared` (`RANGOS_LOL`) y en Prisma en el mismo commit. Maestro, Gran Maestro y Retador no tienen división | Postgres compara los valores de un enum en el orden en que se declaran, así que «rango mínimo Oro II» es `rango >= 'ORO_II'`: una columna, sin tabla de orden ni pares tier-división. Una prueba comprueba que el orden de la base coincide con el de `shared`; reordenar el enum rompería el filtro. Sustituye a la divergencia «Rango competitivo en `Estadistica` y en `Oferta`». |
| `Estadistica.rango` (`RangoLol`, opcional) guarda el rango de **cada captura**; no se guarda en `CuentaGaming` | Es un dato que cambia con el tiempo y que viene de la API en el mismo momento que las demás estadísticas. En la captura queda su historia, útil para la tendencia del jugador (Mis estadísticas); en la cuenta sólo quedaría el último valor. El índice de `Estadistica` pasa a `(jugadorId, juego, capturadaEn)` para leer la última captura de cada jugador. |
| `Oferta.rangoMinimo` pasa de texto libre a `RangoLol`. La migración convierte el texto existente («Diamante II» → `DIAMANTE_II`, «Gran Maestro» → `GRAN_MAESTRO`) en lugar de borrar la columna, y lo que no corresponde a ningún valor del catálogo queda `NULL` | El módulo de ofertas ya está en uso: Prisma generaba `DROP COLUMN` + `ADD COLUMN`, que habría borrado el rango de las ofertas publicadas. Un texto sin división («Esmeralda») no tiene equivalente exacto y no se inventa. El formulario de oferta pasa a un select del catálogo. |

## Integración con Riot

Tarea 2.3 del plan. La única clave disponible es la de desarrollo de Riot; la de
producción (tarea 0.1) no se va a conseguir a tiempo.

| Decisión | Justificación |
| --- | --- |
| **La propiedad de la cuenta se demuestra con un desafío de icono, no con Riot Sign On (OAuth).** El jugador da su Riot ID y servidor (`POST /perfiles/cuentas-gaming/riot`); la API le asigna un icono básico (0–28) distinto del que tiene y, cuando lo pone, lo comprueba en `summoner-v4` (`POST /perfiles/cuentas-gaming/riot/verificar`) y guarda la cuenta con `verificadaEn` | **Divergencia con el documento**, que pide OAuth 2.0 (CLAUDE.md §1). Sin él, buscar el Riot ID bastaría para vincular la cuenta de otro y la verificabilidad sería falsa; el icono sólo lo puede cambiar quien entra en la cuenta, así que mantiene la garantía que importa: los datos son de la API oficial y la cuenta es del jugador. ## Desafío de Riot guardado en el servidor

Ajuste de la verificación por icono (PR #38), tras probarla con una cuenta real.

| Decisión | Justificación |
| --- | --- |
| **El desafío activo se guarda en Redis, por usuario**, hasta que caduca (15 minutos, `MINUTOS_DESAFIO_VERIFICACION`) o se verifica: un hash `proplay:riot:desafio:<usuarioId>` con el JWT de antes (misma audiencia `proplay-verificacion-riot`), lo que ve el jugador y las comprobaciones hechas. `GET /perfiles/cuentas-gaming/riot/desafio` lo devuelve (`{ desafio: … \| null }`), y verificar exige que el token sea **el guardado**, no sólo uno bien firmado | **Riot tarda uno o dos minutos en reflejar el cambio de icono.** Con el desafío sólo en el cliente, el jugador que salía de la vista mientras esperaba (a cambiar el icono, a otra pestaña) lo perdía y empezaba de nuevo con otro icono, que volvía a tardar. Guardado, al volver, recargar o abrir otra pestaña se ve el mismo icono con el tiempo que le queda. Exigir el token guardado es lo que permite invalidar el anterior al generar otro; el JWT sigue impidiendo que el cliente cambie el puuid o el icono y que otro usuario use el desafío ajeno. Redis ya estaba en la arquitectura (RNF-01) y el dato es efímero: no merece tabla ni migración. Va en `perfiles.repository.ts`, el punto de acceso a datos del módulo. Si Redis no responde, 503 `SERVICIO_NO_DISPONIBLE`. |
| La caducidad **sigue en 15 minutos** | Cubre de sobra una demora de uno o dos minutos y unas cuantas comprobaciones; alargarla sólo deja más tiempo para adivinar el icono. Si la demora real resulta mayor, se sube la constante. |
| `POST /perfiles/cuentas-gaming/riot` con un desafío activo **devuelve el existente** si es para la misma cuenta (Riot ID sin distinguir mayúsculas ni espacios, y servidor), sin consultar a Riot; si es para otra, 409 `DESAFIO_ACTIVO`. Un icono nuevo sólo se pide a propósito: «Generar otro icono» (`POST /riot/desafio/regenerar`, otro icono distinto del puesto y del anterior, 15 minutos nuevos y cupo nuevo) invalida el anterior (409 `DESAFIO_REEMPLAZADO` si se usa). «Usar otra cuenta» lo cancela (`DELETE /riot/desafio`) | Reenviar el formulario o abrir otra pestaña no debe cambiar el icono que el jugador ya se puso. Cancelar es necesario para corregir un Riot ID equivocado sin esperar 15 minutos. |
| Que el icono aún no coincida **no es un error**: verificar responde 200 `{ estado: "PENDIENTE", desafio }` con la hora de la comprobación (`ultimaComprobacionEn`) y el icono que vio Riot; si coincide, 201 `{ estado: "VERIFICADA", cuenta }` y el desafío se borra. Sustituye al 409 `VERIFICACION_PENDIENTE` | Es el caso normal mientras Riot se pone al día. La vista lo muestra como aviso informativo («Aún no vemos el cambio…»), no en rojo, y la comprobación automática no llena la consola de errores. |
| **Comprobación automática** en la vista cada 45 s (`SEGUNDOS_COMPROBACION_AUTOMATICA`), contados desde la última comprobación guardada (de cualquier pestaña) o desde la creación; se pausa con la pestaña oculta y para al caducar, al agotar el cupo o al verificarse | El jugador cambia el icono en el cliente del juego y no tiene por qué volver a pulsar: la vista se actualiza sola. 45 s está por debajo de la demora de Riot, así que la primera comprobación útil llega pronto sin gastar cuota de más. |
| **Cupo de comprobaciones propio por desafío: 40** (`MAX_COMPROBACIONES_DESAFIO`; al agotarlo, 429 `COMPROBACIONES_AGOTADAS` y hay que generar otro icono), y una comprobación a menos de **15 s** de la anterior (`SEGUNDOS_MINIMOS_ENTRE_COMPROBACIONES`) devuelve la anterior sin consultar a Riot ni contar. Verificar **deja de pasar por `limiteVinculacionRiot`**, que queda para pedir y regenerar el desafío (las dos rutas que buscan la cuenta) | 15 min / 45 s son 20 comprobaciones automáticas; 40 deja margen para las manuales y una segunda pestaña. Con verificar dentro de los 10 intentos, unos minutos de espera los agotaban. El cupo se cuenta en Redis con un script atómico (dos pestañas a la vez no cuentan doble ni pasan del máximo). En el peor caso un usuario hace 40 consultas a Riot en 15 minutos por desafío, y generar desafíos sigue limitado a 10 cada 15 minutos, frente a la cuota de 100 cada 2 minutos de la aplicación. |
